      How anomaly assignment works
      
        
      
      
      
      
        
      No geometry is moved. This step only creates relationships between anomalies, regularized panels, and rows.
      
        
        
          
      1. The panel with the greatest anomaly-area overlap is evaluated first.
        2. 
          
      2. If it meets the minimum overlap, its panel and row IDs are assigned as a reliable overlap match.
        3. 
          
      3. Otherwise, the nearest panel is assigned only when its edge is within the configured outside-panel distance.
        4. 
          
      4. Anomalies beyond that distance remain unassigned and are flagged for review.
        5. 
        
      
        
      The row ID always comes from the selected panel, keeping the panel and row relationship consistent. Anomalies receive panel_id and row_id; panels and rows receive reciprocal anomaly_ids and anomaly_count.

      Target surface height
      
        
      
      
      
      
        
      DJI RelativeAltitude describes camera height above the takeoff level. For solar-rooftop inspection, the panels are above that level, so using the full relative altitude makes the image footprint and predictions appear too large.
      
        
      Without a reconstructed surface model or DSM, the application cannot determine the solar-panel surface height automatically. It therefore estimates camera-to-target distance as:
      
        
      RelativeAltitude − target surface height
      
        
        
          
      • The default 0 m uses unadjusted DJI relative altitude and does not assume a target-plane height.
        • 
          
      • Use the approximate solar-panel mounting surface or solar-rooftop height above the drone’s takeoff level—not elevation above sea level.
        • 
          
      • The value affects both image footprints and prediction coordinates generated by the new test run.
        • 
          
      • Image alignment keeps the GSD calculated from the camera metadata and this target-plane height; it refines position and residual orientation without changing image scale.
        • 
          
      • Orthophotos and images without usable DJI relative-altitude metadata are not corrected by this option.
        • 
        
      
        
      Important: an incorrect value changes map scale. Verify it against an object with a known dimension. Full reconstruction remains the accurate solution for varying solar-rooftop heights, terrain, or strong perspective.
      
      
      
      
      
        
      
      
    
      
  
      

  
      
    
      
      
      
        
      Align individual images
      
        
      
      
      
      
        
      Alignment runs after lens correction and north-up rotation, and before inference. Corrected positions and residual orientation are saved in camera metadata and used to generate image footprints and prediction GeoJSON.
      
        
      LightGlue image overlaps: uses the open-source LightGlue project by the CVG team to match overlapping neighboring images and jointly refine their relative positions and orientation. GPS provides the soft absolute map anchor. No segmentation or reference GeoJSON is used.
      
        
        
          
      • Images without sufficient verified overlap retain their original metadata.
        • 
          
      • When approximate mosaicing is enabled, the mosaic is created from these final corrected poses.
        • 
        
      
        
      Alignment controls
      
        
        
          
      • Matching quality — Standard. Standard analyses images at up to 768 px with 1,024 SIFT features. High uses up to 1,024 px and 2,048 features. Increasing quality can find more reliable detail in difficult thermal images, but takes more GPU/CPU time and memory. Standard is faster.
        • 
          
      • Matching strictness — Balanced. Strict requires stronger LightGlue scores and more RANSAC agreement, reducing false alignment but potentially leaving more images unchanged. Lenient accepts weaker evidence and may align more images, but increases the chance of matching repeated panels incorrectly. Balanced is the recommended default.
        • 
          
      • Temporal neighbours — 3. Each image is compared with the next three captures, subject to the capture-time safeguard. Increasing it can bridge missing or weak consecutive frames, but adds comparisons and may cross a flight turn. Decreasing it is faster but can fragment the alignment graph.
        • 
          
      • Lateral neighbours — 4. Each image can be compared with up to four GPS-overlapping images from nearby flight strips. Increasing it can connect more strips but costs time and can introduce repetitive-row ambiguity. Setting it lower is safer and faster; 0 disables cross-strip comparisons.
        • 
          
      • Maximum pair rotation difference — 6°. Pairs with a larger visual rotation difference are rejected. Increasing it helps when heading metadata is poor, but accepts more ambiguous transformations. Decreasing it is safer when images are already close to north-up, but can reject valid pairs.
        • 
        
      
        
      Fixed safeguards: GPS consistency, scale limits and final pose-displacement limits remain internal. They prevent a permissive matching choice from moving images to a visually similar but incorrect solar row.
      
      
      
      
      
        
      
      
    
      
  
      

  
      
    
      
      
      
        
      How automatic lens correction works
      
        
      
      
      
      
        
      This optional check estimates radial lens distortion during the current test run. It operates on the actual inference images before north-up rotation and inference. It does not reuse saved camera profiles or infer distortion from image size alone. It uses the existing OpenCV and NumPy dependencies; no calibration package or model is downloaded.
      
        
        
          
      1. Separate optical systems. Group images by camera make, model, sensor source, serial number when available, and dimensions. RGB and thermal sensors are never mixed. Orthophotos are skipped.
        2. 
          
      2. Select eight deterministically. Sort supported files by filename. If there are eight or fewer, examine all of them. Otherwise calculate eight evenly spaced indexes from 0 through image count - 1, including the first and last files. This samples across the complete folder—it does not simply use the first eight images. The indexes are recalculated when files are added or removed; an unchanged folder produces the same sample on every run because no random selection is used. For example, 20 images use indexes 0, 2, 5, 8, 10, 13, 16, 19. For radiometric testing, analyse the decoded thermal view used by inference.
        3. 
          
      3. Trace complete structures. Link local edge evidence into long smooth curves from dominant direction families. Repeated panel grids, building edges, fences, poles, and road markings can provide evidence.
        4. 
          
      4. Choose the best three. Require at least four reliable long traces for an initial sample, rank samples by combined span and support, then use the best three. A sample with three traces may be retained only as a replacement reserve; fewer traces are excluded. A smaller folder may use one or two images when their evidence is sufficient.
        5. 
          
      5. Reject unrelated curves. Natural or genuinely curved objects are treated as outliers unless the same optical centre and radial model straighten several independent traces, direction families, and sampled images.
        6. 
          
      6. Fit one shared model. Jointly estimate one optical centre and radial terms k1/k2 from all fitting traces in the selected images. The system does not calculate separate image parameters and average them. Resolution and focal metadata constrain the calculation but do not determine distortion by themselves.
        7. 
          
      7. Validate independently. Hold back traces from fitting. The model must materially reduce their curvature, win on most held-out traces and every selected image, cover enough of the frame, remain monotonic, and stay inside a safe displacement limit.
        8. 
          
      8. Retry one inconsistent sample safely. If exactly one best-three image disagrees, replace it with the fourth-ranked usable image and validate three images again. If that still fails, make one final fit from the two originally consistent images. The result is applied only when every image in the accepted attempt independently supports it.
        9. 
          
      9. Fail without changing images. If evidence is missing, inconsistent, already straight, or unsafe, preparation stops before writing corrected images. Untick this option to run without correction.
        10. 
          
      10. Apply and record. An accepted model is applied to every image in its matching group at the original width and height. Decisions and fitted values are logged and saved in preprocessing.json.
        11. 
          
      11. Optional photogrammetry export. When the nested export option is checked, write a separate undistorted_images folder before north-up rotation. Files keep their original name, format, dimensions, EXIF/GPS, XMP, ICC profile and timestamps where supported. When both this export and LightGlue alignment are enabled, an additional option can embed corrected latitude/longitude into these copies and write a portable geo.txt sidecar. Absolute altitude is preserved because LightGlue only refines horizontal pose.
        12. 
        
      
        
      Important: automatic calibration cannot be guaranteed for arbitrary natural scenes. Eight evenly spaced candidates are checked and the best three are used. One or two images can still be sufficient for a smaller folder when they contain several long structures across the frame. The images do not need to overlap. When evidence is insufficient, no correction is guessed.
      
      
      
      
      
        
      
      
    
      
  
      

  
      
    
      
      
      
        
      How approximate mosaicing works
      
        
      
      
      
      
        
      This optional workflow creates a quick geolocated mosaic from individual images. It is intended for visual review and inference, not survey-grade orthorectification.
      
        
        
          
      1. Prepare images. Apply selected lens correction first, then rotate every image north-up from its heading metadata.
        2. 
          
      2. Place from metadata. Use EXIF GPS centres and estimated ground resolution for the initial layout. At least two geotagged images are required.
        3. 
          
      3. Calculate full-image footprints. Use each image’s metadata-derived ground resolution to place its complete corrected frame on the mosaic canvas. Source images are not cropped before mosaicing.
        4. 
          
      4. Use final image poses. If Align individual images before inference is enabled, LightGlue runs once on the prepared images and the mosaic uses those corrected positions and residual orientations. Otherwise it uses the original GPS/heading poses.
        5. 
          
      5. Keep safe fallbacks. Images without a verified LightGlue correction remain at their original GPS position.
        6. 
          
      6. Run one inference source. Individual images predicts each prepared frame. Approximate mosaic only builds the mosaic, cuts only the completed mosaic into model-sized tiles, and predicts those tiles. The two modes never run together in one result.
        7. 
          
      7. Blend, then optionally cut. Blend the prepared images at their final poses first. The completed GeoTIFF is cut into model-sized inference tiles only when Approximate mosaic only is selected; individual-image inference keeps the mosaic solely for map review. LightGlue decisions and corrections are recorded in image_alignment.json.
        8. 
        
      
        
      Limitations: a fast 2-D mosaic cannot fully correct terrain relief, strong camera tilt, parallax, poor GPS, missing overlap or large viewpoint changes. Use a full photogrammetry workflow when those effects are significant.
      
      
      
      
      
        
      
      
    
      
  
      

  
      
    
      
      
      
        
      How “Use thermal band” works
      
        
      
      
      
      
        
      This option trains the model from decoded thermal imagery instead of the visible RGB pixels.
      
        
        
          
      1. Scan both splits. Check the selected dataset’s train and valid/val folders for supported radiometric images.
        2. 
          
      2. Decode radiometric data. Use the configured DJI DIRP or FLIR FFF decoder to extract the thermal values.
        3. 
          
      3. Create model input. Normalize the thermal values into a grayscale preview and encode it as a three-channel image so existing Detectron and YOLO models can consume it.
        4. 
          
      4. Pair files by name. Store or reuse previews under each split’s thermal/ folder and record the source-to-thermal mapping in pairs.json.
        5. 
          
      5. Train and identify the model. Train with the paired thermal previews and save thermal mode in the model metadata so testing can select thermal inputs automatically.
        6. 
        
      
        
      Important: this is thermal-as-RGB, not RGB plus a fourth thermal channel. Annotations must match the decoded thermal view. Unsupported or unpaired images are reported in the training logs.
